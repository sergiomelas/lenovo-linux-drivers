CRITICAL ARCHITECTURAL RULES (READ THIS BEFORE RUNNING ANY COMMANDS):
====================================================================================================
- CHECK YOUR REPOSITORY STATE FIRST: If you are starting from a fresh, raw
  extracted tarball, you MUST run 'git init' and create the baseline commit.
  HOWEVER, if you are resuming work inside an existing tree that went through
  this procedure already, DO NOT run 'git init' again, as it will corrupt your
  current repository state and history.
- LEVERAGE YOUR STABLE TREE BASE: By initializing git inside your extracted
  stable tree (or reusing an already initialized one), adding the maintainer's
  subsystem repository as a remote allows Git to download only a few megabytes
  of delta changes instead of gigabytes of history.
- ALWAYS BASE GENERATED PATCHES ON THE UPSTREAM NEXT BRANCH: Even if your local
  stable files look identical, patches destined for upstream MUST be generated
  and tested exclusively on top of the maintainer's 'next' development branch.


====================================================================================================
PHASE 1: THE REBASE (Aligning with the Target Subsystem - SHALLOW FETCH)
====================================================================================================
# 0. Choose your target subsystem from the Reference Sheet below (e.g., HWMON)
# 1. Open a terminal inside your downloaded/unzipped stable source folder (e.g., linux-7.1.1)

# 2. If the folder was downloaded as a tarball, it lacks Git history. Initialize it now:
# (NOTE: Skip 'git init' and 'git add/commit' if you already cloned via git clone)
git init
git add .
git commit -m "Baseline: Official Virgin Linux Stable Source"

Stop here and go PHASE 2 if this is a folder to create a full patch for older versions without yogafan

# 3. Add the alternative subsystem remote repository:
git remote add hwmon https://git.kernel.org/pub/scm/linux/kernel/git/groeck/linux-staging.git

# 4. CRITICAL: Fetch ONLY the latest commit of the next branch to save gigabytes of bandwidth!
# (Using --depth 1 ensures you download only a few MBs instead of the entire kernel history)
git fetch --depth 1 hwmon hwmon-next

# 5. Create your clean development branch anchored EXACTLY on the maintainer's next branch:
git checkout -b hwmon-yogafan hwmon/hwmon-next

# 6. Verify that the baseline driver file exists in the maintainer's tree:
ls -l drivers/hwmon/yogafan.c

For other branch repos see below


====================================================================================================
PHASE 2: THE 6-FILE CHECKLIST (Integration Verification)
====================================================================================================
Before committing, verify all 6 points are correctly addressed in your tree:

[X]  MAINTAINERS
     (Contains your contact info and the list of files you are responsible for).

[X]  Documentation/hwmon/index.rst
     (The master list of documentation where you must add the name yogafan).

[X]  Documentation/hwmon/yogafan.rst
     (The specific description of your driver and the RLLag filter).

[X]  drivers/hwmon/Kconfig
     (The menu entry that allows users to select your driver during a kernel build).

[X]  drivers/hwmon/Makefile
     (The instruction that tells the compiler to build yogafan.o).

[X]  drivers/hwmon/yogafan.c
     (The actual C source code for the driver).


====================================================================================================
PHASE 3: PATCH GENERATION (THE FINAL EXPORT)
====================================================================================================

# 1. Physically copy your files into the folders or modify if rebase:
# - MAINTAINERS
# - Documentation/hwmon/yogafan.rst
# - Documentation/hwmon/index.rst    <<< only this for driver in kernel already
# - drivers/hwmon/Kconfig
# - drivers/hwmon/Makefile
# - drivers/hwmon/yogafan.c          <<< only this for driver in kernel already

# 2. Clean the directory of any non-kernel files
make mrproper

# 3. Force Git to recognize your changes
# Case A: New driver or old kernel setup
git add drivers/hwmon/yogafan.c \
        MAINTAINERS \
        Documentation/hwmon/yogafan.rst \
        Documentation/hwmon/index.rst \
        drivers/hwmon/Kconfig \
        drivers/hwmon/Makefile

# Case B: Driver already integrated upstream (Subsequent cleanups/fixes)
git add drivers/hwmon/yogafan.c \
        Documentation/hwmon/yogafan.rst

# 4. VERIFY: Ensure all modified files are GREEN
#    (ignore the millions of untracked files if coming from Phase 1)
git status

# 5. Commit with the PROFESSIONAL v1 message layout
git commit -s
# (Paste the finalized v1 text into the editor, -s auto-appends Signed-off-by)

# 6. Generate the patch with the correct version suffix
git format-patch -1 --subject-prefix="PATCH"  # For a full standalone patch

git format-patch -v3 --numbered HEAD~1           # For multiple iterations and local history edits

====================================================================================================
PHASE 4: FINAL VALIDATION
====================================================================================================
# 1. Check for coding style and spelling errors:
./scripts/checkpatch.pl --strict --codespell v1-0001-hwmon-yogafan-*.patch

# 2. Verify Build:
scripts/config --module CONFIG_SENSORS_YOGAFAN
make olddefconfig
make drivers/hwmon/yogafan.ko

# 3. Verify Docs:
make htmldocs

5. THE INTEGRATION HUB: LINUX-NEXT
----------------------------------------------------------------------------------------------------
Primary Maintainer: Stephen Rothwell
Email: sfr@canb.auug.org.au
Mailing List: linux-next@vger.kernel.org

PURPOSE:
A daily-generated, read-only integration tree consisting of merged subsystem
sub-trees. This branch is used solely to verify that your standalone patch
does not cause compilation errors or structural merge conflicts with changes
introduced concurrently by other developers before Guenter pushes it upstream.

HOW TO USE YOUR LOCAL STABLE TREE TO CHECK COMPATIBILITY WITH LINUX-NEXT:
1. Open your terminal inside your already initialized stable kernel tree directory.
2. Track the unified integration endpoint without altering your development branches.
3. Download the current daily integration tree baseline reference index.
4. Spawn a temporary execution sandbox branch tracking the day's remote master head.
5. Attempt a dry-run application of your final formatted patch to catch errors.

GIT REMOTE SETUP:
# (Note: Assumes your tree has already been initialized via Phase 1 and fetches with depth 1)
git remote add linux-next git://git.kernel.org/pub/scm/linux/kernel/git/next/linux-next.git
git fetch --depth 1 linux-next master

TESTING INTEGRATION & CONFLICT RESOLUTION RUNS:
# Create an isolated, volatile verification branch directly tracking today's linux-next master
git checkout -b test-compatibilita-next linux-next/master

# Test apply your newly formatted patch to verify zero merge conflicts
git am v1-0001-hwmon-yogafan-Part2.patch

# TROUBLESHOOTING: If 'git am' fails here, a merge conflict has been detected due to concurrent
# subsystems changing mutual architecture definitions (e.g., index.rst, MAINTAINERS, Kconfig).
# Resolve the conflicts locally inside this sandbox to prepare appropriate subsystem re-alignments.
